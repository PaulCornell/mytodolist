Claude: Right now they're stored only in the browser's localStorage, under the key mytodolist.tasks, as a JSON array — that's it in script.js (loadTasks/saveTasks).

Practical implications:
- Per-browser, per-device: tasks saved in Chrome on your Mac won't show up in Safari, or on your phone, or for another user — each browser has its own separate storage.
- No server, no sync: there's no backend; nothing is sent anywhere. That's consistent with how the app runs (open the file or host it statically), but it does mean "other users" each get their own independent, empty list — they don't share your data.
- Not guaranteed permanent: clearing browser data/cache wipes it, and it may not survive in private/incognito sessions.

If you want lists to persist across devices or be shared between users, that requires a backend (a small server + database) — let me know if that's something you want added, or if per-browser local storage is fine for now.

Claude: SQLite is a solid choice for this — recommend a tiny backend API (e.g., Node/Express with better-sqlite3, or Python/Flask) that the browser app talks to over REST, with the .db file committed to .gitignore (not the repo) and persisted on whatever server hosts it. If you want to keep deploy options open (including serverless), the closest thing to "SQLite but hosted" is Turso (managed libSQL, SQLite-compatible) — same mental model and mostly the same SQL, but no server/disk to manage yourself.
